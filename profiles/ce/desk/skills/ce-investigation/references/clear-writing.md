# Clear CE writing — ASD-STE100 inspired

Use short sentences and active voice. Name who must act. Give one action per
instruction. Use the same term for the same concept. Define unfamiliar terms once.
State the answer first. Then give the evidence, relevant limits and next action.
Do not add a generic warning or next step when the question is already answered.
Do not repeat the same fact across sections. Do not explain why an irrelevant
warning does not apply. Let runtime metadata carry routine scope and timestamps.

Keep source facts, organizational knowledge, AI suggestions and actual tool results
separate. Preserve account/region scope, observation time, partial collection and
material uncertainty. A receipt identifies source material; it does not certify a
conclusion. A model critique is not tool validation. A validated draft is not an
executed change. Reassessment means checking fresh evidence after a change.

Do not paraphrase code, commands, identifiers, file paths, hashes or validator
diagnostics to improve style. Preserve the exact returned artifact. Writing guidance
changes prose only; it does not change permissions, evidence, checks or statuses.

Prefer: “After you apply the change, collect fresh evidence.” Avoid: “It may be
prudent to consider undertaking a reassessment subsequent to deployment.”

This is an original CE adaptation inspired by ASD-STE100, not a reproduction of
its controlled dictionary or a claim of formal compliance. The official standard
includes writing rules and controlled vocabulary. Sources:
https://www.asd-ste100.org/about_STE.html
https://asd-ste100.org/STE_downloads.html

Use this guidance in the existing response step. Do not add a rewrite model call
or retry an investigation just for style. Follow the runtime's structured answer
contract when supplied; it owns headings, references and execution status.
